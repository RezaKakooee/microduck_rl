## Running the heavy jobs

Training and rendering both need a GPU. Everything else runs on CPU.

```bash
# train
uv run train Mjlab-Velocity-Flat-MicroDuck --env.scene.num-envs 4096
uv run train Mjlab-VelStand-Flat-MicroDuck --env.scene.num-envs 8192

# anything needing rendering (EGL needs a GPU)
bash src/microduck_lab/render/render.sh clips
```

Training logs to wandb by default, and an unattended run cannot answer a
login prompt. Set `WANDB_MODE=offline`, or run `wandb login` once.

Verified: PPO trains (RTX 3080, 4096 envs, ~1.8 s/iter), checkpoints land in
`logs/rsl_rl/velocity/`, and `scripts/export.py --checkpoint-file <path>`
produces a 61→14 ONNX. Full loop train → export → sim was run end to end.

## Rendering

Offscreen rendering needs `MUJOCO_GL=egl` **on a GPU node** — `libEGL` comes
from the NVIDIA driver, so it needs a GPU. No sudo required.

The interactive viewer (`scripts/infer_policy.py`, keyboard-driven) cannot run
here at all: it needs a display. It is pure CPU MuJoCo + onnxruntime, so the
easy answer is to clone this repo on a machine with a screen and run it there.

Ignore the `EGLError` traceback that prints after a successful render — it comes
from `__del__` teardown, after the frames are written.

`duck_sim.py` exists because the setup `infer_policy.py` does before its loop is

## Traps that cost real time

**`use_projected_gravity` defaults to `False`** in `PolicyInference.__init__`,
but `main()` passes `True`. At the default the policy reads the raw
accelerometer where it expects projected gravity and falls over in ~2 s, looking
exactly like a physics problem. This is the single worst trap in the codebase.

**The timestep must be forced to 0.005.** `infer_policy.py:882` overrides the
XML's 0.002 so decimation 4 lands on the 50 Hz the policies trained at.

**The `alpha_*` policies track poorly.** Commanded 0.3 m/s, they walk 0.13.
Commanded 1.0 rad/s, they turn 0.38. Below ~0.25 m/s commanded they do not move
at all, and **lateral commands produce exactly zero lateral motion** — the duck
cannot strafe. Any closed-loop controller has to aim off rather than sidestep,
and cannot make small corrections. The roller policy is the only one that tracks
its command properly (0.42 vs 0.40 asked).

**Kick and pick both need a standstill.** These policies were trained to start
and end standing; fired mid-stride the motion misses completely even with the
object perfectly placed. Both tasks stop, settle ~3 s, re-check, then fire.

**Kick tolerance, measured:** perfect placement flies 3.9 m, +15 mm forward
error drops to 1.8 m, +30 mm is a clean miss. Lateral is forgiving (±15 mm still
gets 3.3 m). Forward is the axis that must be right.

**The duck shuffles backward ~36 mm as it crouches** for a ground pick. Stand
~81 mm from the object so the drift carries it to the beak.

**Stop *inside* the target window, not short of it.** Because of the deadband, a
duck parked 40 mm short stays there forever — it cannot take a small step.

## The mouth

The RL export fuses the whole head into one rigid body, so the beak physically
cannot open. On the real robot the mouth is the **15th servo**, driven by
`robotd` and excluded from every policy — see `duck-control/src/model.rs`
("Left leg (5) · neck/head/mouth (5) · right leg (5)").

`add_mouth.py` puts the joint back: it lifts the `jaw`/`jaw_soft` geoms onto a
hinge and appends a position actuator as **index 14**, after the 14 servos, so
policies still map straight onto `ctrl[0:14]`. `duck_sim.make_policy` then trims
`n_joints` back to 14 — `PolicyInference` sizes itself from `model.nu` and would
otherwise push the mouth into the observation, making it 64-dim.

Regenerate with:

```bash
cd src/mjlab_microduck/robot/microduck
python3 add_mouth.py robot_allcollisions.xml -o robot_allcollisions_mouth.xml \
    --meshes jaw,jaw_soft --pivot -0.0045 0 -0.040 --axis 0 1 0 --range 0 0.55
```

Those numbers were found by rendering frames and looking at them, not from CAD.
`bottom_head_shell` must NOT be in `--meshes` — it spans the head and see-saws.

## Ice skating (Mjlab-Velocity-Ice-MicroDuck)

Three runs. **The deliverable is `ice_v2_iter4000.onnx`** — a mid-training
checkpoint, not any final policy. It skates at 0.21-0.27 m/s against a 0.3
command across mu 0.05-0.30, feet lifting 15 mm, and does not fall. The
vendored walking policy on the same ice falls at 1.9 s.

| run | final friction | outcome |
|---|---|---|
| v1 | straight to 0.04-0.18, no curriculum | stands still; never learned to move |
| v2 | curriculum to 0.04-0.18 | walked to iter 4000, then UNLEARNED it |
| v3 | curriculum to 0.10-0.25 | keeps lifting feet but marches in place |

The pattern in all three: extra time on ice makes the policy worse, and it goes
**command-deaf**. Measured on the exported ONNX, a forward command changes
v2@4000's actions by 0.30 but v3@7999's by 0.05. v3 ends lifting its feet 6 mm
and travelling 0.00 m — a shuffle that banks `air_time` without propelling.
Training metrics hide this: `air_time_mean` stays at 0.094 and looks healthy.
**Judge an ice run by `Metrics/twist/error_vel_xy` and a rollout, never by
air_time.**

The root cause is physical. Real skating needs ANISOTROPIC friction — a blade is
slippery lengthwise and grippy across, so a skater pushes sideways while gliding
forward. The duck has flat isotropic rubber soles, so at low mu there is nothing
to push against in any direction and a non-propulsive shuffle is the optimum.

**The real fix, not yet attempted:** give the feet anisotropic contact. MuJoCo
supports it — a `<contact><pair>` with 5 friction terms slides 0.17 m one way and
3.61 m the other, verified. Two things to watch: the pair's low-friction
direction follows the CONTACT frame, not world axes (my first test came out
inverted from what I expected), and a `<pair>` overrides `geom_friction`, so the
foot-friction DR event and the whole ice curriculum would have to move to
randomising pair friction instead.

Render clips: `bash src/microduck_lab/render/render.sh ice` on a GPU node.

## Spiral — one-legged glide (Mjlab-Spiral-Flat-MicroDuck)

Goal: roll forward balanced on ONE roller with the free leg extended behind
(figure-skating spiral). Built on the roller velocity recipe.

v1 (10000 iters) produced **a stroking walk on wheels, not a spiral**, and every
metric I had said it worked. The lesson is the metric:

- "single support 92% of the time" means nothing — a WALK is single-support most
  of the time, because it alternates.
- The number that matters is **how long it holds the SAME foot**. v1: mean 0.11 s,
  longest 0.12 s, 108 support swaps in 13 s.
- Free-leg hip read +0.99 rad against a +1.10 target — because a walking swing
  passes through a backward-extended hip. The pose term was paying for walking.

**Judge a spiral run by hold duration, never by single-support fraction.**

Three things were wrong, fixed in v3:

1. Both new terms used smooth ramps from zero, so a 0.11 s swing still collected
   a steady dribble. Now behind a **latch**: below `min_hold_s` on one wheel,
   both pay exactly zero. Ramped 0.30 -> 1.50 s, because a 1.5 s requirement is
   invisible to a policy that cannot yet balance on one wheel.
2. The roller recipe's `gait_symmetry` penalty (-1.0) punishes "lopsided
   left/right foot usage" — the literal definition of a spiral. Zeroed.
3. `single_support_hold` raised 4 -> 8; behind the latch it is the only term
   paying for commitment.

Also fixed earlier: both terms are gated on the wheels actually turning and on
the trunk being upright. `_forward_progress_gate` alone reads TRUNK velocity,
which a forward topple supplies for free.

Two traps for whoever measures this next:
- The foot sites sit at 3-13 mm on the roller model, not tens of mm. A
  foot-height threshold of 45 mm reports 0% single support for every policy.
- v1's checkpoints are `spiral_v1_iter9000.onnx` (no pose at all) and
  `spiral_v1_iter9999.onnx` (the stroking walk).

## Balance board (rocker) — solved, and now playing with it

The duck stands on a plank resting on a loose roller. Long history in
`docs/OPEN_PROBLEM_balance.md`; scripted PD and an open-stance expert both
capped at ~2 s. A whole-body LQR expert then solved it, and a periodic version
makes the duck actively ROCK the board rather than hold it still.

| variant | script | result |
|---|---|---|
| static hold | `task_balance_board_lqr.py` | 60 s, 33/33 stress episodes |
| rocking | `task_balance_board_rocking.py` | +/-6.7 deg at 1.2 Hz, 60 s |
| asymmetric / faster / wider | `task_balance_board_rocking_asym.py` | see below |

Reports: `docs/tasks/balance_board.md`, `balance_board_lqr.md`,
`balance_board_rocking.md`, `balance_board_rocking_asym.md`.

**What the asymmetric variant found** (full numbers in its report):

- The symmetric rocking is a pure sine, so it is left/right symmetric by
  construction. Skewing the phase, biasing the amplitude and adding a slow drift
  all work: one side can swing **57% further** than the other and it still holds
  30 s. Balance does not depend on the symmetry.
- **Faster:** up to **2.0 Hz** at the original 8 deg swing, or **3.0 Hz** at a
  4 deg swing — 2.5x the original rate. Every failure is a **leg touching the
  plank**, i.e. leg clearance, not balance.
- **Wider:** **31.5 deg of range** (+19.5 / -12.0) at 1.2 Hz, holding 30 s,
  against 13.4 deg originally. The ceiling is a **foot lifting off the plank**
  past about 20 deg of tilt — the plank tilts under the sole and, with no
  ankle-roll joint, the sole tilts with it. Same missing joint that closed the
  one-legged pose.
- Frequency is baked into the solved wave, so a new speed **re-solves** it
  (`--frequency-hz`); driving the old wave faster would leave the feedforward
  solving the wrong problem.
- A strong bias is counterproductive for total range: it spends the whole budget
  on one side. Lower the bias, keep the skew high.

**Varied patterns** (`src/microduck_lab/tasks/balance_board/pattern.py`,
`docs/tasks/balance_board_rocking_asym.md` section 7). The asymmetric rocking is
still ONE shape repeating. Making the four parameters functions of time gives:
`choreography` (six named moves, held 34 s), `wander` (sum of sines with
incommensurate periods, never repeats, held 30 s on five seeds), and `finale`
(the choreography plus one move past the limit — rides 35.3 s, then falls).

- The phase must be **integrated** (`theta += 2*pi*f(t)*dt`), not evaluated as
  `2*pi*f*t`. With f varying the direct form steps the phase and the board
  cannot follow.
- The wave does NOT need re-solving per rate for this: the feedback already
  absorbs +/-90% instantaneous-rate swings from the skew term.
- Every range failure, including the scripted one, is a **foot lifting off the
  plank** past about 20 deg of tilt. Same missing ankle-roll joint as the
  one-legged pose.
- `lqr.evaluate` stops the instant a failure trips, so a recording of a fall
  ends while the duck is still upright. Use
  `task_balance_board_pattern.py --show-fall --after-fall 5` to keep filming
  until it is actually on the floor (verified: trunk 47 mm).

**Camera convention, measured:** azimuth **180 = FRONT** (face and lens
visible), 0 = back, 90/270 = sides. An earlier "front" render used 0 and was
actually the back of the head.

**Filesystem trap:** files written on a GPU node can take ~20 s to appear on the
shared disk. Several renders looked like failures when the job had in fact
succeeded. Wait before concluding a render failed.


## Honest limits

- **The grip is a weld, not contact.** There is no closing force; the cube is
  constrained to the jaw and seated on the beak tip. It rides on the tip rather
  than being pinched between the jaws.
- **The mouth hinge is a reconstruction**, approximate in pivot and geometry.
- **Three layouts is not a success rate.** Both tasks were tuned against the
  ahead-left case; the other two happened to work. A sweep over object positions
  would be the honest next step.
- No policy has been trained beyond smoke tests (10 and 3 iterations).

## Next things worth doing

1. Sweep object positions on both tasks to get a real success rate.
2. Retrain walking — the command-tracking gap is the most obvious defect in the
   vendored policies and the clearest thing a retrain would fix.
3. If you want the interactive viewer, run `infer_policy.py` on a machine with a

## Physical love-story correction (2026-09-05)

Use `src/microduck_lab/tasks/love_story/dispenser.py` / `bash scripts/render_duckfilm.sh`.
The supplied `videos/love_story/duck_love_story.mp4` is the old reference; the corrected

See `docs/tasks/duck_love_story.md` for scope and reproduction commands.

The user explicitly chose a visible mechanical egg-release device. The new
set has free eggs preloaded with collidable ducklings, sliding support trays,
physical guide sleeves and motor-driven shell hinges. Only actuator controls
change the simulation after initialization; no root resets, disappearing
props, shell kicks, external forces or mocap decorations. The ring remains
on a solid presentation stand rather than teleporting onto a neck.

Mechanical lessons: capsule shells need compound convex wall panels; a
single concave mesh collides as a filled convex hull. Root stage XML uses
degrees, so the lid joint range must be converted from radians. Sliding trays
need low friction and guide sleeves, or they carry/tip the eggs. Rail
carriages need bearing clearance to avoid redundant rigid contact constraints.
Reverse steering must correct position drift, not hold one fixed heading.
Timeouts now fail the story instead of being silently accepted as completion.
